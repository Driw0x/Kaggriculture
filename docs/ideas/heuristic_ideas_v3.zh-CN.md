<a id="main-idea"></a>
## 核心理念

停止让经济、路径规划、市场处理、容量和执行依赖于各自独立的近似值。让每个子系统都消费一个共享的预测、一个预留模型、一个任务表示和一个经过验证的市场日历，从而确保规划器中某一部分接受的决策，也能被其他部分所接受。

`v3` 完整继承了 [`v2`](heuristic_ideas_v2.zh-CN.md)。由于 `v2` 已经继承了 `v1`，因此所有未变更的 `v1` 规则通过传递性仍然可用；`v3` 只有一个直接前驱版本。

<a id="core-ideas-added-in-v3"></a>
## v3 新增的核心理念

<a id="1-one-shared-forecast-for-all-planner-decisions"></a>
### 1. 所有规划决策共享一个预测

维护从当前绝对时间点到游戏结束的单一推导状态预测。

该预测仅对变更后受影响的部分进行投影，并追踪：

- 种植与动物状态；
- 浇水、喂养和照料；
- 生存状态；
- 产量与生产日期；
- 施肥；
- 衰减与饱和度；
- 维护需求；
- 资源与可收获产出；
- 地块占用与未来释放。

生产、布局、土地管理、市场和终局逻辑均从该相同预测中读取数据。

<a id="2-economy-placement-and-expansion-become-one-coherent-plan"></a>
### 2. 经济、布局与扩张形成一个连贯的计划

经济策略应产生有明确时间点的承诺，而非孤立的愿望。

它仅评估在游戏结束前仍能创造正价值的生产活动，并包含完整链条：

`production -> maintenance -> resources -> harvest -> return -> DROP -> SELL`

它还包含现金、雇佣、库存和市场时段。

`DECIDE_LAND_PURCHASE()` 仍源自 `v2`，但现在它消费的是这个通用计划，而非维持一个独立的经济近似值。

<a id="3-generate-dependency-aware-taskgroup-objects-directly"></a>
### 3. 直接生成具备依赖感知的 `TaskGroup` 对象

用从原始任务直接生成稳定组的方式，替代多阶段从原始任务到任务包和物流的转换过程。

一个 `TaskGroup` 包含：

- 位置；
- 有序操作；
- 优先级；
- 截止时间；
- 所需资源；
- 预估价值；
- 依赖关系；
- 可选的工人分配。

前置条件继承其所依赖项的紧迫性。

稳定标识能够在生成被反复调用且没有实质性状态变化时，防止任务重复出现。

<a id="4-merge-routing-capacity-logistics-and-hire"></a>
### 4. 合并路由、容量、物流和`HIRE`

工人分配应评估将一组任务插入路由的真实成本。

插入成本包括：

- 行驶时间；
- 操作时间；
- 取货；
- 等待资源；
- 返回和`DROP`；
- 截止时间；
- 库存影响；
- 市场影响。

如果一组重要任务仍然无法分配，则测试一个新的工人，并包含斐波那契雇佣成本、生成、可用性周期、剩余路线容量、行驶、返回和截止时间。

只有当实际使目标任务可行时，`HIRE`才会被接受。

<a id="5-prefer-small-local-route-improvements-over-a-complex-global-solver"></a>
### 5. 优先选择局部小规模路线优化，而非复杂的全局求解器

在获得可行路线后，尝试在任务组之间进行有限的移动或交换。

仅当路线成本严格改善且不违反截止时间或预订时，才接受变更。

如果一组任务同时包含紧急收获和可选替代，则先移除可选替代，再单独尝试收获。

目标是构建一个更好的启发式规划器，而不是一个通用的VRP系统。

<a id="6-use-one-stock-and-market-calendar"></a>
### 6. 使用一个库存和市场日历

所有`BUY`、`SELL`、`HIRE`及相关市场意图都必须通过一个经过验证的日历进行排期。

日历：

- 按依赖关系排序操作；
- 确保融资销售发生在其所支持的采购或雇佣之前；
- 遵守每周期最多10个订单的限制；
- 模拟现金流、库存、预订和价格；
- 将冲突反馈给相关任务。

第11个订单绝不能被静默丢弃。

延迟采购会无效化相关的取货或播种。延迟雇佣会基于旧的可用性周期无效化路线容量。

<a id="7-replan-by-repairing-only-the-affected-future"></a>
### 7. 仅修复受影响的未来部分进行重新规划

不要在每次观察变化后都广泛重建规划器。

首先询问该变化是否影响可行性、预期收益的符号或所选择的经济行动。如果不影响，则保持当前计划。

当需要修复时：

- 识别局部原因；
- 保留已确认的事实和已承诺的路线前缀；
- 保留已支付的工人和仍然有效的路线；
- 仅释放无效的未来预订和受影响的路线后缀；
- 仅重新生成受影响的任务组；
- 仅重新分配新加入或被取代的任务组。

当多个路线共享相同的资源或市场依赖时，局部问题仍可能传播到多个路线。

<a id="8-integrate-endgame-constraints-into-every-decision"></a>
### 8. 将终局约束融入每一个决策

终局逻辑不应作为最后的清理步骤。

每当无法在游戏结束前通过完整的现金流链偿还该决策时，就拒绝新增生产、动物或扩张。

`installation + production + harvest + return + DROP + SELL`

另外移除没有剩余可变现效果的维护或支出，例如无用的迟施肥料、护理、购买或可选雇佣。

从最终清算截止日期倒推，规划最后一次收获、返还、丢弃和销售。

<a id="9-turn-known-edge-cases-into-explicit-verification-cases"></a>
### 9. 将已知的边缘情况转化为明确的验证案例

规划器应被测试以验证具体不变量，包括：

- 扣除已携带库存后的精确饲料领取；
- 种子预留防止并发过度种植；
- 自`HIRE`开始的一格时间后，雇佣工人的可用性；
- 在溢出`DROP`之前而非在溢出时释放棚屋容量；
- 修复市场冲突超过10个订单，而不是截断它们；
- 当不存在额外盈利生产时，拒绝土地；
- 拒绝未来维护不可行的土地。

<a id="key-invariants"></a>
## 关键不变量

- 每个子系统使用相同的预测和预留。
- 在状态不变的情况下重复生成，不得重复规划工作。
- 物流是路线可行性的组成部分，而不是事后补丁。
- 雇佣只有在使其原本不可行的重要工作变得可行的情况下才有效。
- 市场依赖关系被显式安排，绝不会被静默截断。
- 延迟的市场行为会使其依赖的未来行为无效。
- 重新规划必须保留已承诺的有效工作，并仅修复受影响的后缀部分。
- 每一个新的经济决策在游戏结束前都必须完成其完整的现金流出链。

<a id="what-v3-changes-relative-to-v2"></a>
## v3 相较于 v2 的变化

`v3` 并未主要增加新的游戏规则。它重新组织了规划器，以确保现有规则的一致性评估。其核心改进是连贯性：一个统一的预测、具有依赖感知的任务组、集成的分配与雇佣、一个统一的市场日历、局部修复，以及在所有地方的终局感知可行性。
