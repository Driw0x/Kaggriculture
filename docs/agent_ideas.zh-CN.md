# 智能体想法

<a id="1-state-memory"></a>
## 1. 状态记忆

维护一个持久的农场状态内部记忆，以便智能体能够追踪种植区和动物在各步骤中的状态，而不仅仅基于当前动作进行推理。

-   **种植区：** 保持一个已种植地块列表，包含其位置及相关状态，例如作物类型、种植时间、生长阶段或预期收获状态。
-   **动物：** 保持一个动物列表，包含其位置及相关状态，以便追踪其发展过程和所需操作。
-   随着游戏进程推进，持续更新存储的状态，并在种植区或动物不再对应存储状态时删除或重置相关条目。

**状态：** 已实现。保留的规划器会从观察中刷新作物和动物状态，并在地块生产类型发生变化时同步存储的生产状态。

<a id="2-general-path-management"></a>
## 2. 通用路径管理

将移动视为一条路径，而非独立选择每次移动。智能体应确定需要前往的位置，并遵循一条合适的路径前往该目标。

-   将路径管理应用于所有空间动作，包括在种植区、动物区、市场位置或其他相关位置之间的移动。
-   在播种时，定义一条高效路径，覆盖所有需要播种的地块，而不是独立选择地块。
-   相同的通用路径逻辑可以用于其他空间动作序列，以减少不必要的移动。

**状态：** 已实现。空间任务现已嵌入时间安排的工人计划中。任务间的移动时间直接包含在计划中，并根据完整行程从四个入口地块中选择绕行路径，而非作为独立移动处理。

<a id="3-opponent-state-memory"></a>
## 3. 对手状态记忆

维护对手可观察的农场状态内部记忆，以估算其潜在的未来产量及其对市场的可能影响。

- 追踪对手在各步骤中的可观察种植区和动物状态。
- 基于其当前状态，估算其潜在的未来产量。
- 估算对手可能在何时以及生产多少资源。
- 利用此信息预测市场供应的潜在增加。
- 在评估未来市场价格和市场风险时，考虑对手的产量估算。

**状态：** 部分实现。CHI10可以在市场估算中包含可见/公开的对手供应预测，但跨步骤的对手状态记忆并未包含在保留的基准中。

<a id="4-priority-based-task-planning"></a>
## 4. 基于优先级的任务规划

从明确的任务优先级构建每日计划，而不是将所有动作视为同等重要。

- 优先处理必须的维护工作，例如作物存活、收获/重种周期以及动物喂养和护理。
- 仅当有足够的工人容量时，才安排可选的扩展或除草工作。
- 保留任务之间的依赖关系，确保动作按有效顺序执行。
- 为相应的作物链之前明确设定生存浇水的前置关系。
- 当有其他工人依赖其进行喂养时，优先安排小麦交付。
- 在不危及必要工作的前提下，将空闲的工人容量重新用于可盈利的低优先级任务。

**状态：** 通过时间任务生成、显式前驱关系、任务的必选/可选标志以及有界分配搜索实现。

<a id="5-dynamic-workforce-management"></a>
## 5. 动态劳动力管理

根据预期工作量和额外容量的经济价值，动态选择工人数量。

- 搜索完成所需任务所需的最小劳动力规模。
- 考虑新雇佣工人的实际起始时间步和生成位置。
- 检查在当前可用工人的情况下，必要行动是否仍能在每日时间截止前完成。
- 将新增一名工人的预期价值与下一个斐波那契雇佣成本进行比较。
- 当新增工人的预期额外利润不再足以抵消其成本时，停止雇佣。
- 不要人为设定最多十名农夫的上限。

**状态：** 已实现。

<a id="6-conditional-watering-and-production-timing"></a>
## 6. 条件性灌溉与生产时机

避免在灌溉或持续生产不再创造有用价值时消耗行动。

- 仅在作物生存必需或在收获前必须灌溉时才进行灌溉。
- 跟踪作物生长周期，确保收获和重新种植决策符合生产周期。
- 避免种植或重新种植无法在最终销售前产出的作物。
- 将终局可行性原则同样应用于新动物。
- 一旦无法在时间上完成额外的盈利收获，就停止维持生产。

**状态：** 已实现。

<a id="7-dynamic-production-selection"></a>
## 7. 动态生产选择

根据预期盈利能力而非固定的开张后布局来选择新的生产内容。

- 评估空地或即将空出地块上的作物和动物。
- 在评估中包含购买成本、饲料成本、人工成本、占用时间和空间使用。
- 使用预期市场状态来估算边际收入。
- 仅保留盈利且可负担的生产选择。
- 将选定的生产计划转换为所需的种子、动物和小麦市场订单。

**状态：** 已实现。

<a id="8-profit-aware-land-expansion"></a>
## 8. 盈利意识的土地扩张

将土地购买视为一项必须由其可安装生产的价值所证明的投资。

- 估算新区域可提供的生产价值。
- 包含种子、动物、饲料和额外雇佣成本。
- 在购买土地前检查其可负担性。
- 避免在剩余时间不足以收回投资时进行延迟扩张。
- 优先选择有用生产空间，而非自动扩张。

**状态：** 已实现。

<a id="9-market-aware-valuation-and-sales"></a>
## 9. 市场意识的估值与销售

在决定生产内容和销售时机时，使用预期市场演变情况。

- 基于当前库存、预期自身供应、商店需求和可见的对手公开供应，估算未来价格。
- 按单位预测销售量而非假设单一固定售价。
- 通过替代的供应/时间情景评估对手不确定性，而非假设单一精确的对手未来销售模式。
- 在适当情况下持续出售收获产品，而非等待一次全局清仓。
- 当需要现金或压力升高时，更积极地出售产品，同时保留用于活跃动物的麦子储备。
- 对价格敏感产品进行销售计量，以避免不必要的价格影响。
- 保持肥料独立可售。
- 在第29天末尾附近清仓剩余可售库存。

**状态：** 已在保留的CHI9/CHI10规划器家族中实现。

<a id="10-shed-and-inventory-logistics"></a>
## 10. 舍饲与库存物流

将舍饲视为一个受限的物流节点，而非仅作为被动存储位置。

- 在返回产品或收集资源时，引导工人前往最近的有效舍饲访问格子。
- 在选择返回路径时，使用所有四个有效的舍饲访问格子。
- 考虑工人携带的产品以及当前回合内已存入的产品。
- 在规划收获和销售时，防止舍饲溢出。
- 当动物喂养依赖于同一天内生产的麦子时，协调麦子收获、舍饲投放及后续取回。
- 使用可用性周期表示共享资源，以便工人可以等待另一名工人后续存入的资源。
- 允许一名已携带麦子的工人为主动创建一个明确的交付任务给另一名工人。

**状态：** 已实现。

<a id="11-animal-production-management"></a>
## 11. 动物生产管理

根据动物的生产状态、饲料依赖性以及剩余可用容量来管理动物。

- 在适当情况下，在开始下一个喂养/护理周期前收获可获得的动物产品并收集肥料。
- 确保依赖饲料的工作延迟至有足够的麦子可用为止。
- 当待处理奖励和已持有生产量已接近动物的可用容量时，避免不必要的CARE操作。
- 在估算动物生产价值时，包含CARE效果。
- 当未来无有用销售或估算剩余动物利润变为非正时，停止动物维护。
- 在减少路线碎片化的情况下，保持动物工作的分组。

**状态：** 已实现。

<a id="12-observation-checked-execution"></a>
## 12. 观察验证执行

当当前观察结果不再匹配生成该动作堆栈时所依赖的假设时，不要盲目执行先前生成的动作堆栈。

- 将计划中的工人操作与当前游戏状态进行验证。
- 在返回动作前，按引擎执行顺序检查共享种子库存、舍饲库存、工人拾取、格子突变和舍饲容量。
- 当格子内容或生产类型发生变化时，重新同步生产状态。
- 当产品在当前回合内被存入时，重新计算相关销售和库存信息。
- 将无效的计划动作替换为`PASS`，而不是盲目执行过时的动作。

**状态：** 在`chi10_temporal.py`中实现。

<a id="13-bounded-temporal-scheduling"></a>
## 13. 有界时间调度

使用明确的时间来安排工作，而不是仅将任务按顺序分配给每个工人。

- 为每个任务表示其位置、动作序列、预期价值、必需/可选状态以及前驱依赖关系。
- 为每个工人表示其当前位置、当前时间、库存和时间动作序列。
- 在可行性检查中包含移动时间、拾取时间、资源等待时间和动作时间。
- 根据每种数量在哪个时间步变为可用来预留共享库存。
- 强制执行实际的每日截止时间，包括为在剧集结束前出售存入商品而要求的较短最后一天截止时间。
- 使用一个小的有界束搜索来保留多个工人/任务分配方案，避免穷举式调度变得过于昂贵。
- 允许跳过可选任务，当这样做能带来更优或更可行的后续计划时。

**状态：** 已实现。

<a id="14-tick-by-tick-worker-replanning"></a>
## 14. 逐时间步工人重规划

不要在一天内持续执行一条固定的工人路线，当游戏状态可能已发生变化时。

- 在每次代理调用时，从当前观察结果中重建实时的任务集。
- 使用实际的工人位置、库存、观察到的仓库库存和当前方格状态重新计算工人分配。
- 围绕已变为可用的资源、已完成的任务或不再有效的动作进行重新规划。
- 保留高层次的每日生产、招聘、土地和市场规划，同时持续重规划工人的执行层。
- 仅记录当前观察结果下的新时间计划，并在执行前验证当前时间步的动作。

**状态：** 在`chi10_temporal.py`中实现。

<a id="15-public-shop-order-production-prior"></a>
## 15. 公开商店订单生产优先级

当多个生产候选者已有相似经济评分时，使用已公开解锁商店的顺序作为微弱的需求信号。

- 将每种作物或动物映射到其生产的产品。
- 将该产品与前两个已解锁商店的需求进行比较。
- 仅应用一个很小的倍数，以确保底层边际利润模型仍是主要决策标准。
- 仅使用当前公开观察中已存在的信息。

**状态：** 在`chi11.py`中实现。第一个已解锁商店在候选产出匹配相应商店需求时应用8%的生产评分倍数，第二个已解锁商店应用3%的倍数。

<a id="16-public-farm-similarity-and-clone-aware-sales"></a>
## 16. 公开农场相似性与克隆感知销售

利用两个公开可见农场之间的重复相似性作为弱信号，表明同时行动可能导致可避免的市场冲突。

- 从作物数量、动物数量、已解锁区域和农场手数量构建一个紧凑的公开签名。
- 要求相似性在多个连续回合中持续存在，才激活任何特殊行为。
- 不要使用对手身份、隐藏库存、剧集标识符、回放查找或未来动作。
- 当条件激活时，减少普通销售批次大小，而不是替换基础销售策略。
- 绝不限制最终清算。

**状态：** 在 `chi11.py` 中实现。检测从第 48 步开始，要求在连续 24 轮中签名距离最多为 2，且可在第 160 步激活。当条件激活时，普通 SELL 数量上限为 10 单位。

<a id="17-market-impact-aware-sell-ordering"></a>
## 17. 市场影响感知的 SELL 排序

当同一市场动作中已存在多个 SELL 订单时，优先选择对自身价格影响最显著的订单。

- 使用当前公开市场库存和现有的单位价格模型，估算销售后的价格。
- 根据估算的即时价值损失对现有 SELL 位置进行排序。
- 仅重新排序 SELL 订单。
- 保留所有非 SELL 市场位置，不创建新的销售。

**状态：** 在 `chi11.py` 中实现。

<a id="18-standalone-submission-packaging"></a>
## 18. 独立提交打包

当开发版本本需依赖另一个本地代理模块时，确保竞争代理可直接作为单个 Python 文件提交。

- 将保留的基础代理实现直接嵌入提交文件中。
- 从最终竞赛文件中移除项目本地导入。
- 保持公共 `agent(obs)` 入口点不变。
- 保留基础代理行为，并在单次基础代理调用周围应用实验性叠加层。

**状态：** 在 CHI 11 中实现。`chi11.py` 包含 CHI 10 的基础规划器和 CHI 11 的叠加层，全部集成在一个自包含文件中。

<a id="19-public-route-baseline"></a>
## 19. 公开路线基准

将一个强大的公开固定路线代理作为独立的实验基准，而不是将其动作序列直接混合进 CHI 规划器中。

- 以可读的 Python 格式存储公开路线，以便每天、每小时、每个动作均可检查和修改。
- 在第一个基准中精确保留原始动作序列。
- 将基于路线的实验与 CHI 规划器家族分开，以便清晰地归因改进。
- 将公开路线作为竞争参考，先在该路线基础上提升鲁棒性，再修改其宏观策略。

**状态：** 在 `jet.py` 中实现。原始压缩的 v27 路线通过机械方式扩展为 719 个可读动作，且未改变其内容。

<a id="20-staged-runtime-fallbacks"></a>
## 20. 分阶段运行时回退

当一个可选运行时修正引发异常时，不要丢弃整个路线周期。

- 在应用运行时叠加层之前，保留基础路线动作。
- 将 WEED 修复、最终清算和 SELL 排序分别隔离在独立的受保护阶段中。
- 若一个叠加层失败，保留最后有效的动作，而不是返回全为 `PASS` 的回合。
- 保留完整的 `PASS` 回退机制，用于在无法恢复任何可用路线动作的情况下使用。

**状态：** 在 `jet1.py` 中实现。

<a id="21-observation-based-final-liquidation"></a>
## 21. 基于观察的最终清算

用实际可销售库存为基础的清仓机制，替代路线带中固定的最终销售数量。

- 从`episodeSteps`中检测到最后可执行的步骤。
- 读取实际仓库内容，而不是依赖预录制的最终数量。
- 包含在构建最终卖出订单前，由同时间步`DROP`动作所存入的产品。
- 尊重配置的市价订单限制。
- 在每一个更早的步骤中，保持路线不变。

**状态：** 在`jet1.py`中实现。
